## 背景

本任务是并行组 A 的内核，紧接 M1-01 脚手架。它让后续模块（M1-04 起）有可注册、可按场景过滤、单模块失败不拖垮整站的宿主。M1-03 Config 可并行；M1-04 / M1-05 / M1-09 依赖本任务合并后再挂模块。M1 出口要求 `WPCY_KERNEL=v4` 打开时不加载 `framework/`。

## 行为规格

以 `docs/4.0-rewrite-plan.md` §5.3 为准，冲突时以该节为准并在报告说明。

接口完整签名（照抄 §5.3，不得改方法名或参数）：

```php
interface Module {
    public function id(): string;
    public function register(): void;
}

interface ConditionalModule extends Module {
    public function enabled(Config $config, Environment $environment): bool;
}
```

`Config` 在落地里对应 `Config\Repository`（`docs/dev/module-authoring.md`）。本任务可先定义 `src/Core/Config.php` 为窄接口（`get` / 存在性），M1-03 再让 Repository 实现它；**不要**在本任务实现四个 option。

补充约定（`module-authoring.md`，方法名可微调、语义不可改）：

```php
public function dependencies(): array { return []; }
public function contexts(): array { return [ 'admin', 'frontend' ]; }
```

`ModuleRegistry` 伪代码（必须按此语义实现，变量名可改）：

```
function boot(scene):
  mods = topological_sort(registered)   # 按 dependencies()
  for m in mods:
    if scene not in m.contexts(): continue
    if m is ConditionalModule and not m.enabled(config, env): continue
    try:
      m.register()                      # 钩子只在这里挂
    catch Throwable:
      logger.error(...)
      diagnostics.record(m.id(), error) # 不得 error_log 后假装成功
      continue                          # 不阻断后续模块
```

`WPCY_KERNEL` 接入点（**不要给会破坏 3.x 的改法**）：

- 常量默认**未定义**。未定义或值不是 `v4` 时，路径与现网 3.x 完全一致：照旧 `require` autoload、照旧 `new \WenPai\ChinaYes\Plugin()`。
- 判断写在现有 `if (file_exists(CHINA_YES_PLUGIN_PATH . 'vendor/autoload.php'))` **分支内部**、旧 `Plugin` 实例化**之前**（今天实例化在该 `if` 块之后、`register_*_hook` 附近，见 `wp-china-yes.php`）。推荐形态：autoload 已 `require` 之后，`if ( defined( 'WPCY_KERNEL' ) && 'v4' === WPCY_KERNEL ) { \WenPai\ChinaYes\Core\Plugin::boot(); return; }`，然后才走到现有 `new Plugin();`。
- 禁止：把 `new Plugin();` 删掉、把 3.x 常量定义挪走、在 `file_exists` 失败分支启动新内核、默认把常量设为 `v4`。
- 开 `v4` 时不实例化旧 `Plugin`，因而 `framework/` 不被 3.x `Base` 拉起。关时零行为差。

单元测试必须覆盖总计划验收要点：注册顺序、依赖解析、单模块抛异常不阻断其它、场景过滤（admin/frontend/rest/cli/cron）；开关关时行为与 3.x 完全一致。
