## 背景

4.0 是新品分发，不是 3.9.3 换号。更新检查走云桥；`plat-api` 的 `VersionCheck.php` **保持 3.9.3（LTS）**，不得把 4.0 写进该端点。灰度：先文派自有站 **7 天**，再全量（本任务书；运营目标对照定稿 §7.6 90 天采用 ≥ 70%）。

README 总表 M4-04 行「plat-api 停止返回 3.x 以外版本」与「保持 3.9.3」同义：plat-api 只服务 3.9.x。**不改 README。**

## 行为规格

### 发布链（M2-08 已有，本任务跑）

对照 `docs/release/4.0-runbook.md`：

1. `main` 冻结，HEAD CI 全绿（php 矩阵以统筹填入的下限为准，占位 8.0；quality；frontend；plugin-check；package；wordpress；e2e）。
2. 版本三处已是发版号（RC 或产品改定的 `4.0.0`）。
3. CI `package` ZIP：含 `build/index.js` 与生产 composer 依赖；不含 `.git`、`tests/`、`docs/`、`src/Admin/app/`、`framework/`、`Service/`、`client/`、`composer.json`（仓根）、`yahnis-elsts`。SHA-256 对应该 HEAD。
4. 旧候选 ZIP / SHA 作废。

### 分发切云桥

4.0 更新检查 **只** 登记到云桥 `updates.wenpai.net`（定稿 §7.1-7）。步骤由 devops / 已授权执行者做，插件仓代理不改生产机。核：一台 4.0 站的更新检查返回本版与该 ZIP。

插件内不得再构造 `api.wenpai.net/china-yes/version-check`（M4-01 已删 `Service/Update.php` + PUC）。若授权后仍发现该 URL，阻断发版。

### plat-api 3.x 通道

`plat-api` `VersionCheck.php` 保持 **3.9.3**（LTS）：version / download_url / requires / tested / requires_php 不改成 4.0。4.0 **不上** 该端点。本任务执行者即使用有 SSH 权限，也不得改该文件。

### 灰度（定稿 §7.6 + 本任务书）

1. 文派自有站先升 4.0，观察 **7 天**（Fatal、镜像回源、绑定、装回 3.9.x 抽检）。
2. 再全量打开云桥 4.0 更新。
3. 之后 90 天盯采用率（目标活跃站 ≥ 70%）、滞留 3.6/3.7、更新检查是否到达那些站——运营动作，代码仓只在验证文档留检查表，不在插件里做采用率 UI。

官网 `/changelog` `/news` 用 M4-03 经产品侧改定的文案；本任务不擅自改 wpcy.com。

### 回滚

站点：停用 4.0 → 装 3.9.x ZIP → 启用。`wp_china_yes` 仍在。禁止发版说明教用户「清 option」。

## 与 3.x 的关系

3.9.x LTS 继续 plat-api + 既有包域。两条产品线两条通道。4.0 发版不得把 plat-api 的 3.8/3.9.3 JSON 改成 4.0 来「顺便推送」。
