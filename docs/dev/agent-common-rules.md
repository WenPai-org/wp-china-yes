# 通用规则（每份任务书都附带）

这份文档解决什么问题：执行代理每次领任务都要同一套工作方式、交付格式和禁区。本文是 `~/wt/grok-tasks/COMMON-RULES.md` 在产品仓内的副本；统筹会把两边同步。除原文副本外，本节之后「增补」是本次 SOP 任务按统筹决定加上的条，不得在执行时删掉。

你是执行者，不是决策者。任务书里写死的范围、命名、禁区不得自行更改；发现任务书有矛盾或做不到的地方，**停下来在最终报告里写明**，不要自己拍板绕过去。

## 工作方式

- 当前目录是一个独立的 git worktree，分支已建好。只在当前目录内改文件。
- 上下文文档在 `.grok-context/`（已被 git 忽略），先读完再动手。**不要把 `.grok-context/` 提交进 git。**
- 可以 `git add` / `git commit`（提交信息用中文或英文都行，写清为什么）。**禁止 `git push`、禁止切换分支、禁止 `git reset --hard`、禁止改 `master`/`main`。**
- 不要联网获取外部资料（web 搜索已禁用）；需要的信息都在任务书和仓库里。
- 不要装新的系统级依赖；仓库自带的 `composer` / `python3` / `php` 可以用。
- 不写任何"遥测""匿名数据""隐私开关"之类面向用户的文案（产品定稿：报告常开、界面不露出）。

## 交付

完成后输出一份**最终报告**（中文），必须包含：

1. 改了哪些文件（`git diff --stat` 原样贴出）。
2. 每条验收标准的实际执行命令和输出摘要（不要只写"通过"）。
3. 任务书里你没做、做不到、或有疑问的项，逐条列出原因。
4. 提交哈希（`git log --oneline -5`）。

审批者会先跑你的验收命令再看 diff；没有命令输出支撑的"完成"视为未完成。

## 测试夹具规则（2026-09-05 补）

- 测试**不得**读取 `.grok-context/` 里的任何文件（该目录被 git 忽略，换个检出就不存在）。需要的样本复制进 `tests/fixtures/` 并提交。

## 增补（SOP，2026-09-06）

- **给原文，不给范围**：颜色、尺寸、文案、路径写具体值，不写「大约/范围/类似」。见 [`task-book-template.md`](task-book-template.md)。
- **线索标猜测**：统筹给的原因分析若未验证，必须写「猜测：」前缀，执行者按证据纠正并在报告写明。
- **报告写完再退出**：等 CI 时先写「CI run \<id\> 进行中，本地验收如下」，不要空着报告等门禁。
- **UI 任务先看原型再动手**：无 [`design-sop.md`](design-sop.md) 认可记录的 UI 任务书无效。先打开原型和带编号规格，再写代码。
- **不得用「占位/TODO/EmptyTable」交付用户可见区域**。空状态、错误状态、降级状态要有对应实现与文案，见 [`copy-guidelines.md`](copy-guidelines.md) 与 DoD。

## 不做什么

- 不把这份副本改回与统筹决定冲突的旧句。仓内副本与 `~/wt/grok-tasks/COMMON-RULES.md` 的同步由统筹做，执行者只改任务书允许的路径。
- 不把「增补」写进用户界面。
- 不 push、不切分支、不 `git reset --hard`。
